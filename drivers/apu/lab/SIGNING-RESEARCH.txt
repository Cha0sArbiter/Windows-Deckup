Finding
-------
The previous conclusion that modifying any catalog-covered file necessarily
forces the executable driver to require Test Mode was too broad. Package
installation validation and executable signature validation are separate
checks. Modifying a configuration file still invalidates the original
package's signature for that file, but the unchanged kernel still has its
original hash covered by the unchanged Microsoft-signed vendor catalog.
Whether Windows accepts the complete arrangement at installation and on
an actual normal boot must be tested; it is not proven by SignTool alone.

Hardware identity investigation
-------------------------------
In this startup path, the revision argument originates in a parser at RVA
0xE0880. It calls ntoskrnl!IoGetDeviceProperty with property number 1
(hardware IDs), parses the DEV_ and REV_ text, and returns those values to
the caller at RVA 0x53098. Thus this particular check uses the Windows
hardware-ID property; it is not a direct PCI configuration read here.
That observation does not establish that changing a registry string would
persist, alter all other checks, or constitute a supported device identity
override. Windows documents hardware-ID properties as read-only, and the
PCI revision register is read-only through standard PCI access. No hardware
identity, registry hardware ID, PCI register, or firmware was changed.
The configuration-only candidate avoids needing to spoof that identity.

Limits
