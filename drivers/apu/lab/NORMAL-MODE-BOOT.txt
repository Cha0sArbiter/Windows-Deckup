The user requested this boot trial on 2026-10-05 after the reload/resume
investigation. It tests whether the unchanged ASUS kernel can actually
load with TESTSIGNING disabled. The prior configuration-only sleep/resume
failure is unresolved. A successful boot does not establish anti-cheat
compatibility, game stability, or reliable sleep.

Prepare-Normal-Mode-Boot.cmd requests the ordinary Windows administrator
prompt. The helper verifies the LCD Deck identity, working prototype,
both complete package manifests, both already-staged INF hashes, and
Microsoft kernel signing policy for every candidate .sys file. It backs
up BCD and records the state before changing the driver selection.

A single SYSTEM task first performs a read-only self-test, then guards
preparation. After verifying staged/shared files, the helper uses
SetupAPI's DI_NOFILECOPY, DI_DONOTCALLCONFIGMG, and
DI_NEEDREBOOT flags to request installation without live removal or
reenumeration of the display device. The selected registered INF and
service kernel/configuration hashes must match the candidate before
TESTSIGNING is set OFF for the next boot. This does not itself restart
Windows, prove that the resident kernel changed, or prove normal boot.
The successful selection and normal boot above verify this path on this
Deck and exact package; other devices/builds are untested.

Wait for ReadyForNormalModeRestart in normal-boot/<trial>/prepared.json
and status.json. Then restart Windows manually. The startup SYSTEM task
opens a 180-second acknowledgment window after it begins running. Once
the display works, report that result promptly; the agent verifies the
new boot, live Code Integrity, candidate INF, Code 0, version, and exact
kernel/configuration hashes before running Mode Keep. You can also run
Keep-Normal-Mode-Driver.cmd within the window. A successful acknowledgment
causes the SYSTEM watcher to remove its one-time recovery task.

Without acknowledgment, the watcher restores TESTSIGNING ON BEFORE
selecting the patched oem50.inf fallback for a deferred restart. It checks
the selection and requests a recovery restart. After the next boot it
waits briefly for GPU initialization, records the recovery result, and
removes its task. No recurring app automation is created.

Recovery depends on Windows, Task Scheduler, and SetupAPI remaining
responsive. It cannot recover a complete kernel hang. If needed after
Windows becomes usable, Restore-Test-Mode-Prototype.cmd requests admin
rights and invokes this trial's recovery path; it enables Test Mode,
selects the prototype for reboot, and requests restart. Keep all local
packages, trust certificates, registered vendor catalogs, and scripts in
place throughout the trial. Do not use the older Test-Mode-only helper
while the live kernel is in normal mode.
